# Ibex SKY130HD ABC return-134 qualification

## Result

Classification: **PASS_WITH_KNOWN_TOOL_WARNING**.

The pinned Yosys/ABC9 warning is deterministic and its continuation behavior
is understood. The direct ABC9 helper aborts on an internal assertion, but it
has already produced `output.aig`; pinned Yosys therefore emits a warning and
continues through the XAIGER2/mapping flow. The resulting synthesis artifacts
are reproducible and fully technology-mapped. The underlying ABC defect remains
a known tool warning; no workaround or tool replacement was used.

## Failure and reproduction

The original log reports the failure during `abc_new` / `ABC9` technology
mapping of the top `ibex_core` module. The attempted helper command was:

```text
"/OpenROAD-flow-scripts/tools/install/yosys/bin/yosys-abc" -s -f /tmp/yosys-abc-yUVQPx/abc.script 2>&1
```

It returned code `134` while processing `ibex_core`. The exact synthesis-only
run, with the original Ibex SKY130HD configuration, 10 ns clock, RTL, SDC,
platform, and synthesis settings, reproduced the same warning and completed
with wrapper/target return code `0`.

The preserved ABC9 script and inputs were then run directly without changing
options:

```text
"/OpenROAD-flow-scripts/tools/install/yosys/bin/yosys-abc" -s -f /run-debug/yosys-abc-4DRbzz/abc.script
```

Direct result: return code `134`, followed by `Aborted`. The last meaningful
ABC diagnostic was:

```text
giaTim.c:799: ... Gia_ManDupCollapse_rec(...): Assertion `Gia_ObjIsAnd(pObj)' failed.
```

The preceding repeated diagnostic was `Tim_ManGetCiArrival(): Input arrival
times of the box are not up to date!`. This proves a deterministic ABC internal
assertion/abort at process level. It does not identify a deeper root cause in
ABC beyond that assertion.

Pinned Yosys source `tools/yosys/passes/techmap/abc9_exe.cc` constructs the
helper command at lines 286–291. At lines 336–340 it treats a nonzero exit as
a warning when `output.aig` exists, and as an error only when it does not.
The preserved `output.aig` exists, so the warning/fallback behavior is
intentional in this pinned source. Yosys continued through XAIGER2, later
mapping passes, statistics, checks, and Verilog output.

## Synthesis artifact validity

The original and clean reproduction generated byte-identical `1_2_yosys.v`
files (SHA-256
`af554c007865145dc19f1eeb543ff7cbbaa4046428e5fea0cbd854d89d25cab2`). Both
have zero generic `$` cell-type lines and 15,658 SKY130HD-mapped cell lines.
The reproduction also generated `1_synth.odb` and returned successfully.

Read-only OpenDB inspection of the reproduction checkpoint found:

- design: `ibex_core`
- total instances: `14,043`
- SKY130HD instances: `14,043`
- non-SKY130HD instances: `0`
- unique masters: `82`

The original `1_synth.odb` has the same mapped-instance result. The physical
flow explicitly reads `1_synth.odb` at floorplan initialization, so the
checkpoint used by the reference physical run is the synthesis artifact
qualified here. The synthesis report also ends with `Found and reported 0
problems.`

## Tool/resource observations

The container reports `aarch64`; Yosys is `0.68+post` and `yosys-abc` is the
ARM64 `ABC 1.01` executable from the pinned image. The container cgroup reports
unlimited memory and zero `oom`, `oom_kill`, and `oom_group_kill` events. No
OOM evidence was found. The direct `Aborted` result and assertion identify the
observed process-level failure as an ABC internal abort, not a demonstrated
resource kill.

## Remaining uncertainty

The exact underlying ABC algorithmic defect is not isolated beyond the pinned
assertion in `giaTim.c:799`. This qualification proves that Yosys accepted the
partial ABC9 artifact and produced a valid, fully mapped synthesis checkpoint;
it does not prove that ABC9 completed every intended optimization before the
abort, nor does it qualify timing, physical sign-off, or silicon behavior.
